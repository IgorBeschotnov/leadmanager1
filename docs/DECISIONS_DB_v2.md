# РЕШЕНИЕ: Модель Company (лид) v2 + свап AUTH_USER_MODEL

**Модуль:** 20_БАЗА_ДАННЫХ
**Статус:** DRAFT v0.1 (готово к переносу в центральный журнал решений)
**Дата:** 2026-09-02

---

## Контекст

Скрапер/импорт (40) поставляют и нормализуют данные под утверждённую здесь
структуру — не наоборот. Дедупликация по ЄДРПОУ ненадёжна (не все источники
его отдают), поэтому дедуп смещён на этап тёплого звонка и опирается на
телефон. Нужна классификация лида по видам деятельности для точного КП.
Появились команды (90_АДМИНИСТРИРОВАНИЕ), лид должен быть к команде
привязан и неизменяем после назначения.

## Ключевые решения

1. **`region`** добавлен рядом с `city` отдельным полем.

2. **Дедупликация — мягкая, не constraint.** Добавлено `phone_normalized`
   (только цифры первого номера из `phones`), вычисляется автоматически в
   `save()`. Не unique — просто индексируемое поле для сверки оператором на
   звонке. Полноценная нормализация (отдельная таблица телефонов) —
   отложена, не требуется сейчас.

3. **`category` → `categories` (ManyToMany).** Лид может относиться к
   нескольким видам деятельности одновременно (нужно выбирать несколько).
   Финальный список категорий — вопрос бизнес-логики, здесь только форма
   хранения.

4. **`team` — прямое поле на `Company`**, не выводится через `assigned_to`.
   FK на `accounts.Team` (модель из 90_АДМИНИСТРИРОВАНИЕ).
   - Новый лид создаётся с `team = null` (сырой пул).
   - `team` проставляется, когда менеджер создаёт по лиду карточку
     (берёт в работу).
   - После этого `team` **неизменяема** — проверка в `save()`, не DB
     constraint. Лазейка `force_team_change=True` — под owner override.
   - Всё остальное на лиде редактируется свободно.

5. **`contact_person`** — заготовка на будущее, простое CharField.
   Выделять в отдельную модель `Contact` только если реально понадобится
   несколько контактов на компанию.

6. **История смены `stage` не дублируется отдельной моделью.** Используется
   `access_audit_log` из 90_АДМИНИСТРИРОВАНИЕ (`action='lead_status_changed'`,
   `target_type='lead'`). Отдельная `StageChangeLog` не нужна.

7. **AUTH_USER_MODEL заменён на `accounts.User`.** Свап дешёвый сейчас (новый
   проект `leadmanager1`, миграций ещё нет) и дорогой после появления данных
   — поэтому сделан сразу, а не отложен. `accounts.User` = `AbstractUser` +
   `telegram_id`, `team`, `description`, `access_revoked` — по структуре
   `users` из 90_АДМИНИСТРИРОВАНИЕ_роли_и_доступы.md (v0.2).
   `assigned_to` (Company) и `operator` (CallLog) указывают на неё.

## Изменения к текущей модели (diff)

| Поле | Было | Стало |
|---|---|---|
| `city` | есть | без изменений |
| `region` | — | добавлено |
| `category` | `ForeignKey` | `categories` — `ManyToManyField` |
| `phone_normalized` | — | добавлено, авто в `save()` |
| `contact_person` | — | добавлено |
| `team` | — | добавлено, `FK(accounts.Team)`, неизменяемо после назначения |
| `assigned_to` | `FK(auth.User)` | `FK(accounts.User)` |
| `CallLog.operator` | `FK(auth.User)` | `FK(accounts.User)` |

## Открытые вопросы (не решаются здесь)

- Порядок распределения сырых лидов командам (очередь vs рандом) —
  40_СКРАПЕР_ИМПОРТ / 90_АДМИНИСТРИРОВАНИЕ, сознательно отложено.
- Точные права по capability (что может `collector` vs `outreach` vs
  `sales` на уровне действий с лидом) — 90_АДМИНИСТРИРОВАНИЕ.
- Финальный список ~10 категорий видов деятельности — 10_БИЗНЕС_ЛОГИКА.
- `access_revoked` как флаг vs запись в `access_audit_log` с историей
  отзывов — 90_АДМИНИСТРИРОВАНИЕ.
